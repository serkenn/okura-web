# 情報アーキテクチャの手法：okura-web の作り直しのために

この文書の役割：画面のオブジェクト（もの）の型と、ナビゲーションを作り直すときに使う手法をまとめる。手法ごとに中身・手順・何を決めるかを書き、最後に okura-web への当てはめ方を書く。
画面ごとの「何を載せるか」は `docs/information-design.md` が扱う。この文書はその手前の「何が画面の単位になるか・どうつながるか」を扱う。

---

## 1. 手法

### 1.1 オブジェクト指向UI（OOUI。上野学・藤井幸多／ソシオメディア）

**中身**：画面を「タスク（動詞）」ではなく「オブジェクト（名詞）」を起点に組む。ユーザーは先に対象を選び、次に操作を選ぶ（**名詞→動詞**）。
動詞→名詞（タスク起点）の画面は、手順が決まっていてモードになりやすい。対象から入る画面なら、途中でやめて別の対象を選ぶだけで済む（モードレス）。
ソシオメディアの記事は、タスク起点からオブジェクト起点に組み直すと画面の数が 1/5〜1/20 になった例を挙げている。また、タスクは事業の中で変わりやすいがオブジェクトは変わりにくいので、拡張と保守にも強いとしている。

**手順**（書籍 2-6・第3章の3段階）

| 段階 | やること | 決まること |
|---|---|---|
| 1. オブジェクトの抽出 | 要求・タスクの文から**名詞を抜き出す** → メインのオブジェクトを選ぶ → **多重度**（1対多など）・**プロパティ**（属性）・**アクション**（タスクから引き出す）を決める | 画面の単位になる「もの」と、その中身・できること |
| 2. ビューとナビゲーション | メインのオブジェクトごとに**コレクション**（一覧。少ない属性）と**シングル**（1件。多い属性）のビューを作る → ビューどうしの呼び出し関係を決める → メインのオブジェクトから**ルートナビゲーション**の項目を選ぶ | 画面の一覧・遷移・いちばん上のメニュー |
| 3. レイアウトパターンの適用 | ルートナビとビューの配置、コレクションの表示と絞り込み、作る・消す・変えるのパターンを当てる | ペインを並べるか（大きい画面のマスター・ディテール）、画面を移るか（スマホ） |

**オブジェクトかどうかの目安**（ソシオメディア「OOUI – オブジェクトベースのUIモデリング」）
- 同じ属性を持つものが複数ある。
- それらに共通の操作ができる。
- 「受信」「フラグ」のような**動詞・状態はオブジェクトにしない**。状態はコレクションの絞り込みとして扱う。
- 「一覧」「カレンダー」「地図」は見せ方（ビュー）であって、オブジェクトではない。

**マスター・ディテール**：コレクション（左）で選ぶと、シングル（右）に出る。操作の結果を左から右へ一方向に流すと理解されやすい。
同じ UI のモデルのまま画面の単位を変えれば、スマホでは「一覧 → 押すと1件の画面」になる。

**ナビゲーションの決まり方**：ルートナビは「メインのオブジェクトのコレクション」を並べたものになる。ほかのオブジェクトには、関係をたどって行く（例：人 → その人の書類）。
動詞のメニュー（「知る」「調べる」「注文する」）は中身が想像しにくいので、名詞に直す（同記事のイントラネット・ピザの例）。

### 1.2 OOUX と ORCA（Sophia Prater）

**中身**：OOUI と同じ考え方を UX の作業手順にしたもの。ORCA は Objects・Relationships・Calls-to-action（CTA）・Attributes の頭文字。
この4つを「発見 → 要件 → 優先度 → 表現」の4巡で繰り返す（4巡・15の手順。各巡の中身の詳細は有料の講座にあり、公開の資料では概要だけ）。

| 要素 | 問い | 成果物（Prater の A List Apart の記事） |
|---|---|---|
| Objects | ユーザーが気にする名詞は何か（noun foraging） | 目的・調査の文から名詞に印を付ける。繰り返し出る名詞がオブジェクトの候補。抽象語（「露出」など）は外す。行為（コメントする）からオブジェクト（コメント）を推す。オブジェクトがたどる**状態**も書き出す |
| Relationships | どのオブジェクトの中に、どのオブジェクトが入るか。何対何か | 入れ子のオブジェクト（nested objects）。**入れ子の関係が、そのまま文脈のナビゲーションになる** |
| CTAs | そのオブジェクトに対して、誰が何をできるか | CTA の目録：CTA ごとに理由・**誰が押すか（役割・権限）**・どこに出すか・流れの複雑さ・優先度・未解決の問い。オブジェクトの状態と役割で出す・出さないが変わる |
| Attributes | 何でできているか | 中身（本文・画像）と**メタデータ（並べ替え・絞り込みに使うもの）**を分ける |

- 要素を大事な順に並べ替える（force-rank）。この順位が1列（モバイル）の画面の並びになる（「モバイルファーストとは優先度を強制すること」）。
- 「上のナビゲーションは非常口」（Val Jencks の言葉の引用）：利用者はふつう、ページの中身（関係したオブジェクトへのリンク）から次へ移る。グローバルナビは非常口として置く。
- CTA の目録は、システムの設計から操作の流れの設計へ渡すための道具。オブジェクトごとに操作を出していくので、機能の漏れが減る。

### 1.3 Jesse James Garrett の5段階モデル（The Elements of User Experience）

**中身**：UX を、抽象から具体へ積み上がる5つの面に分ける。下の面の決定が、上の面で選べるものを縛る。
各面は「ソフトウェアの道具としての面」と「情報（ハイパーテキスト）としての面」の二面を持つ。okura-web はその両方にあたる（記録・計算の道具であり、結果と根拠を読む場所でもある）。

| 面（下から） | 決めること | 道具としての要素 | 情報としての要素 | okura-web での問い |
|---|---|---|---|---|
| 1. 戦略 Strategy | 何のために作るか | 事業の目的・ユーザーのニーズ | 同左 | 家族の誰が、どんなときに、何を片付けたいか |
| 2. 要件 Scope | 何を作り、**何を作らないか** | 機能の仕様 | コンテンツの要件 | どの機能・どの情報を載せるか（e-Tax へ送らない、などの除外も） |
| 3. 構造 Structure | 要素どうしの**つながりと区別** | インタラクションデザイン | 情報アーキテクチャ | オブジェクトとその関係、カテゴリの中身、流れの順序 |
| 4. 骨格 Skeleton | 要素の**配置** | インターフェースデザイン | ナビゲーションデザイン | 一覧・詳細の並び、メニューの置き場所（情報デザインは両側にまたがる） |
| 5. 表層 Surface | 見た目 | 視覚デザイン | 同左 | 色・字・アイコン |

**作り直しに当てはめる（下から上へ）**
1. 今の画面を面ごとに書き出し、**問題がどの面にあるか**を見分ける。メニューの並べ方の問題に見えても、原因は下の面（構造・要件・戦略）にあることが多い。
2. 問題があるいちばん下の面から作り直す。そこより上の面は、作り直した面に合わせて作り直す前提にする。
3. 各面の作業は、下の面が全部終わるまで待たなくてよい。ただし、**下の面が終わる前に、上の面を終わらせない**（Garrett の勧め）。
4. 表層（見た目）は最後に作る。見た目を整えても、構造の問題は直らない。

この依頼の「機能ごとに作ってきた」は、構造の面（3）を飛ばして、要件（2）を骨格（4）にそのまま写した状態にあたる。

### 1.4 情報アーキテクチャの4つのシステム（Rosenfeld・Morville・Arango）

| システム | 決めること | 中身 |
|---|---|---|
| 組織化 Organization | 何を、どの軸でまとめるか | **正確な軸**（五十音・時系列・地理）と、**曖昧な軸**（話題・タスク・利用者・メタファー）。構造は階層・データベース（メタデータで絞る）・ハイパーテキスト。組織化を先に決め、それをナビゲーションとラベルの土台にする |
| ラベリング Labeling | まとまりと項目を何と呼ぶか | 専門用語か一般の言葉か（「所得」と「手取り」）。まとめてから名前を付けるので、組織化と切り離しにくい |
| ナビゲーション Navigation | どこにいて、どこへ行けるか | グローバル・ローカル・**文脈の**ナビゲーションと、補助（サイトマップ・索引・ガイド） |
| 検索 Search | 探して見つける | 検索の対象・結果の出し方。4版ではメタデータ・統制語彙の章もある |

okura-web の「年分・年度」は時系列の正確な軸、「人」は利用者の軸、「家計簿・申告」は話題の軸。どの軸を上に置くかを決めるのが、組織化の決定にあたる。

### 1.5 メンタルモデル（Indi Young）

- **中身**：人が目的に向かって何を考え、何をし、何を感じるかを、聞き取り（listening session。製品の話をせずに、本人の考えを聞く）から集める。
- **手順**：発言を行動の単位（箱）にする → 似た箱をまとめて**塔**にする → 塔を**心の空間**（大きな目的）にまとめる → 図の上半分に人の行動、下半分に**今の機能**を、支えている塔の下に並べる。
- **決まること**：支えのない塔（作るべきもの）と、どの塔も支えていない機能（減らせるもの）。
- okura-web では、親・子の「年末に扶養を気にする」「領収書をもらう」「申告の時期に慌てる」のような塔の下に、今の画面を並べると、機能ごとに作った画面のどれが、どの塔を支えているかが分かる。

### 1.6 JTBD（Jobs to be Done。Christensen ほか）

- **中身**：「ジョブ」とは、**ある状況で、人が成し遂げたい進歩**のこと（HBR 2016）。人は進歩のために製品を「雇う」。
- **使い方**：オブジェクトの型を作りすぎないための**検査**に使う。オブジェクトを全部並べたのに、「今年、母を扶養に入れたままでいいか知りたい」というジョブに答えるには5つの画面をたどる必要がある、という状態を見つける。
- 書き方の例：「〈状況〉のとき、〈したいこと〉をしたい。そうすれば〈進歩〉できる」。
- オブジェクト起点の構造（OOUI）は「何がどこにあるか」を、ジョブは「なぜ来たか」を決める。ホームと通知は、ジョブを入口にしてオブジェクトへ渡す場所にする。

### 1.7 タスク起点とオブジェクト起点の使い分け

| | オブジェクト起点（名詞→動詞） | タスク起点（動詞→名詞・ウィザード） |
|---|---|---|
| 向く | 何度も来る・順序が自由・あとから見直す・同じものを色々な目的で使う | **めったにしない**・慣れていない・**順序に意味がある**・枝分かれで不要な手順を隠せる |
| 向かない | 決まった順に全部を済ませる作業（漏れが出る） | 繰り返す作業（毎回全部の手順を踏む）・手順をまたいで見比べる作業・途中で止まる作業 |
| 例 | 書類・入出金・人・質問の答えの見直し | 初回の設定・年に一度の申告書への写し・招待リンクで答える |

- NN/g の勧め：ウィザードは、たまにしかしない処理に向く。全体の手順と今の位置を見せる・途中で保存して戻れる・各手順にほかの画面の情報を要らなくする・ボタンを「次へ」でなく、その手順でする操作の名前にする。
- **段階的な開示（staged disclosure）**＝ウィザード。各手順が互いに依存しないときだけ使う。
- 組み合わせ方：ウィザードの各手順は、オブジェクト（人・書類・判断・欄）の**ビューを順に見せるだけ**にし、データはオブジェクトに置く。ウィザードを閉じても、同じものがオブジェクトの画面から見える・直せるようにする。

### 1.8 モバイルのナビゲーション

- **下のタブ＝いちばん上のオブジェクト**：タブバーは、重みが同じ3〜5の行き先を置く場所で、**操作（撮る・再計算）は置かない**（Material 3・Apple HIG）。5つを超えると入らない（NN/g）。
- **ハブ・アンド・スポーク**：ホームに全部の行き先を並べ、移るたびにホームへ戻る形。1回の訪問で1つの用事だけ済ませるアプリに向く（NN/g）。移るたびに1手増えるのが欠点。
- **段階的な開示（progressive disclosure）**：最初は頻繁に使うものだけを見せ、まれなものは2段目に送る。**2段を超えると迷いやすい**（NN/g）。最初の画面に出ていること自体が「これは大事」という合図になる。
- ハンバーガー・「その他」は見つけにくい。隠すなら、中身のリンク（文脈のナビゲーション）で補う。

### 1.9 カードソートとツリーテスト

- **オープン**：カテゴリを決めずに、参加者が分けて名前を付ける（メンタルモデルとラベルを知る）。**クローズド**：決めたカテゴリに入れてもらう。
- 分けたカテゴリが正しいかの確かめには、**ツリーテスト**（逆のカードソート。「〇〇はどこにありそう？」とメニューの木だけで探してもらう）のほうが向く（NN/g）。
- okura-web の利用者は家族3人なので、統計は取れない。3人に、オブジェクトの名前を書いたカード（20枚ほど）を分けてもらい、そのとき口にした言葉を集める。そのうえで、新しいメニューの木でツリーテストをする。

## 2. okura-web への当てはめ

### 2.1 今のナビゲーションの見立て（`frontend/src/Shell.tsx` の NAV・TABS）

| 今の項目 | 種類 | 気になる点 |
|---|---|---|
| ホーム | ハブ（ジョブの入口） | 役割は正しい。「やること」がオブジェクトに渡されているかを確かめる |
| 家計簿・入出金・口座 | 家計簿：集計のビュー。入出金・口座：オブジェクト | 家計簿は入出金のコレクションの集計のビューで、オブジェクトではない。登録待ちは入出金の**状態** |
| 書類（upload） | オブジェクト（原本） | 経路の名前は upload（動詞）。中身は書類のコレクション |
| 要確認（inbox） | **状態の一覧** | AI の提案・読み取りの未確認・取り込み待ちの入出金・質問は、どれも「人が確定する前」の状態。入口が3つ（要確認・入出金の登録待ち・質問）に分かれている |
| 記録 | オブジェクト（事実） | 書類との関係（書類 → 記録）、人との関係が画面で見えるか |
| 家族 | オブジェクト（人） | 人のシングルのビューが `person`・`results/<人>`・`forms/<人>` に分かれている |
| 質問 | 状態（未確定の判断） | 「判断」というオブジェクトの、答えていないものの絞り込み。答えた判断の一覧と見直し（replaces）の置き場所がない |
| 計算結果・申告書 | 出力のビュー | 「人×年分（年度）×制度」の結果。申告書は所得税の結果の様式のビュー |
| 設定 | 混在 | メンバー（人）・依頼（質問）・カテゴリ（家計簿）・市区町村の値（計算の入力）はオブジェクトの一部。本当の設定は共有・ログイン・AI・AI連携 |

まとめ：今のメニューは、**機能の出どころ**（家計簿・記録・確定申告）でまとめられている。同じオブジェクト（人・判断）の入口が複数ある一方で、状態（要確認・質問・登録待ち）がオブジェクトのような顔をしてメニューに並んでいる。

### 2.2 オブジェクトの候補（仮説。家族への聞き取りで確かめる）

| オブジェクト | 主な属性（★＝絞り込み・並べ替えのメタデータ） | 関係 | CTA（誰が） |
|---|---|---|---|
| **人**（家族の一人） | 表示名・続柄・★アカウントの有無・同意 | 書類・記録・判断・結果を持つ。管理する人 | 足す・同意を変える（本人・管理者）・質問を頼む（管理者） |
| **書類**（原本：写真・PDF） | 画像・★種類・★人・★年・★状態（未登録・AI 読み取り・確かめた） | 1つの書類 → 0〜多の記録 | 撮る・読み取りを頼む（人・AI）・**確かめる・登録する（人だけ）** |
| **記録**（事実台帳の行） | 値・★種類・★人・★年・★出どころ（人・AI の提案）・根拠の書類 | 書類・人・入出金に結びつく。訂正・取消しの履歴 | 訂正・取消し（理由つき、人だけ）・提案（AI） |
| **判断**（人が決めること） | 問い・選んだ答え・決めた人と日時・★状態（未回答・回答済み・見直し）・候補ごとの違い | 人・年に属する。`replaces` で見直しが連なる | 答える（本人・管理者・招待の端末）・提案（AI）・見直す |
| **結果**（人×年分・年度×制度） | 値・★状態（確定・未確定・対象外・予測）・境目・根拠・版 | 記録・判断から作られる。様式の欄を持つ | 見る・根拠をたどる・再計算（人・AI） |
| **入出金** | 日付・金額・★口座・★カテゴリ・★状態（取り込み待ち・登録済み） | 口座に属する。申告の記録と結びつく | 登録・分類・分割（人）・取り込み（API） |
| **口座** | 名前・残高・★共有か自分だけ | 入出金を持つ | 残高を調整（人） |
| **提案**（AI から） | 中身・出どころ・★状態（要確認・確定・却下） | 確定すると記録・判断・入出金になる | **確定（人だけ）**・却下 |

- **年分・年度**はオブジェクトにせず、画面全体の**文脈（年の切り替え）**にする候補。所得税は年分・住民税と国保は年度で、ずれがある。どちらで見せるかはラベルの問題として、okura-gov の値をそのまま出す。
- **要確認**は、「人が確定する前」の状態の提案・書類・入出金・判断を横断で集めたコレクションのビュー（ホームの「やること」）にする。オブジェクトにしない。
- CTA の目録には、**役割の列（本人・管理者・家族・招待の端末・AI・外部のエージェント）**を必ず作る。AGENTS.md の「人が決めることを AI に決めさせない」は、そのまま「確定の CTA の『誰が押すか』の列は人だけ」という表の決まりになる。同意（share_numbers など）は、**役割ごとに見える属性**の表として書く。

### 2.3 タスク起点のまま残す流れ

| 流れ | 理由 | 作り方 |
|---|---|---|
| **確定申告書への写し**（年に1回） | めったにしない。作成コーナーの欄の順に写すので、順序に意味がある | ウィザード：年分と人を選ぶ → 未回答の判断 → 未確定の値の確認 → 欄を順に写す（「写した」の印） → 済み。途中で止めて戻れる。各手順は判断・結果・欄のビュー |
| **初回の設定**（世帯・自分・家族を足す） | 1回だけ。順序がある | ウィザード。終わったら人のオブジェクトの画面へ |
| **撮る → 確かめる → 登録** | 書類をもらった直後の短い用事（1回の訪問で1つの用事） | 撮るボタン（操作）はタブではなく、ホームと書類の一覧に置く。登録の結果は書類・記録のオブジェクトに残る |
| **招待リンクで答える**（ゲスト） | その人あての判断に答えるだけ | 1問ずつの流れ。ほかには行けない（今の guest_ok のとおり） |
| **年末の扶養の見直し**（任意） | 年に1回。境目と判断の見直しを順に確かめる | 人ごとの短いチェックの流れ。中身は結果の境目と判断のビュー |
| **AI の会話の「この内容で登録します」** | 会話の中の操作 | カードは提案オブジェクトのビュー。確定は人。会話を閉じても提案の一覧に残る |

### 2.4 ナビゲーションの形（仮説）

- **下のタブ（4＋その他）**：ホーム（やること・ハブ）／家族（人 → その人の結果・判断・書類・申告）／書類／お金（入出金・口座・家計簿の集計）。
  「質問」は件数のバッジとしてホームと人の画面に出す。撮る・再計算・AI はタブに置かず、上のバーや一覧の操作として置く。
- **大きい画面**：左のメニューは同じオブジェクトを並べ、マスター・ディテール（一覧と1件を横に並べる）にする。
- **文脈のナビゲーション**を主にする：結果の値 → 根拠の記録 → 原本の書類、人 → その人の未回答の判断、入出金 → 結びついた申告の記録。
- **設定**は本当の設定（共有・ログイン・AI・AI連携・計算の対象）だけにし、メンバーは「家族」、依頼は「判断」、カテゴリは「お金」、市区町村の値は計算の入力として、それぞれのオブジェクトのそばへ移す候補にする。

### 2.5 作業の順序

| # | 面（Garrett） | 作業 | 成果物 |
|---|---|---|---|
| 1 | 戦略 | 親・子のジョブを書く（`docs/information-design.md` の読み手とジャーニーを土台に）。家族3人に短い聞き取り | ジョブの一覧（10個ほど） |
| 2 | 要件 | 今の機能・画面・API を全部並べ、ジョブに結びつける（メンタルモデルの図の「下半分」）。どのジョブも支えない機能に印 | 機能 × ジョブの表 |
| 3 | 構造 | README・AGENTS.md・ジョブの文から**名詞を拾う**（noun foraging） → オブジェクトの目安で選ぶ。状態・ビューを外す | オブジェクトの一覧 |
| 4 | 構造 | 関係（入れ子・多重度）の表 | オブジェクト × オブジェクトの表 |
| 5 | 構造 | CTA の目録（役割・状態・人だけの確定） | CTA の表 |
| 6 | 構造 | 属性（中身とメタデータ）・役割ごとに見える範囲 | 属性の表 |
| 7 | 構造 | タスク起点で残す流れを決め、各手順がどのビューを使うかを書く | 流れの一覧 |
| 8 | 構造 | ラベル（日本語の名詞。`tools/labels_vocab.json` に合わせる）。カードソート → ツリーテスト（家族3人） | メニューの木 |
| 9 | 骨格 | コレクション・シングルのビュー、ルートナビ（タブ4＋その他）、マスター・ディテール、開示は2段まで。経路を `#/<オブジェクト>/<ID>` に揃え、今の経路から転送する | 画面の一覧・ワイヤー |
| 10 | 表層 | 見た目。今の部品をなるべく使い回す | 画面 |

- 1〜8 は紙（表）だけで進められ、コードは変えない。9 で初めて `main.js` の NAV・VIEWS を変える。
- データの層（台帳・API）は変えない前提で始める。オブジェクトの表を作ると、API に足りないもの（例：答えた判断の一覧）が分かる。その分だけ API を足す。

## 3. ナビゲーションを見直すときのチェックリスト

- [ ] いちばん上のメニューの項目は、どれも**名詞**で、メインのオブジェクトのコレクションか、ハブ（ホーム）か。動詞・状態・機能の出どころの名前になっていないか
- [ ] 1つのオブジェクトの1件（例：ある人）に行く経路は**1つの正本の画面**にまとまっているか。結果・申告書・判断は、その画面から行けるか
- [ ] 状態（要確認・登録待ち・未回答）は、オブジェクトの一覧の**絞り込み**か、ホームの横断の一覧になっているか。似た「待ち」の入口が複数ないか
- [ ] タブは3〜5で、重みが同じか。タブに操作（撮る・再計算）が入っていないか
- [ ] どの値からも、根拠の記録 → 原本の書類へ、**文脈のリンク**で戻れるか
- [ ] 開示は2段までか。「その他」の中にしかない、よく使うものはないか
- [ ] タスク起点の流れ（申告書への写し・初回の設定・招待）は、全体の手順と今の位置を見せ、途中で止めて戻れるか。閉じたあと、同じものがオブジェクトの画面で見えるか
- [ ] CTA の目録で、**確定・記録の CTA が人のセッションだけ**になっているか。AI・外部のエージェント・招待の端末に出ていないか
- [ ] 同意によって見えない属性・オブジェクトが、メニューの件数・合計からも漏れていないか（自分だけの口座など）
- [ ] 未確定・対象外・予測の状態が、一覧（コレクション）でも消えずに見えるか
- [ ] ラベルは家族の言葉か（カードソートで出た言葉）。英字の欄名・ID・JSON が出ていないか
- [ ] 主なジョブ（「母を扶養に入れたままでいいか」「この領収書を片付けたい」）を、ホームから**3手以内**で済ませられるか（ツリーテストで確かめる）
- [ ] 年分（所得税）と年度（住民税・国保）の違いが、年の切り替えで混ざらないか
